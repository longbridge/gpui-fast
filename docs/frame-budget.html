A 120 Hz display gives a frame 8.33 ms, and the wall clock never reports less than that, so builds are compared on the CPU time the main thread spends on each frame — where gpui builds, lays out and paints. Extracted gpui used nearly all of it: the grid ran at the edge of the refresh whether it was still or changing. Now the still grid takes half the frame, and one where every cell changes two thirds of it.

The gain tracks how much actually changed

The horizontal axis is the share of cells whose text differs from one frame to the next. The baseline is a flat line: it costs the same whether anything changed or not, because it rebuilt every layout node and reordered every primitive either way. The current tree follows the real workload — the quieter the interface, the cheaper the frame — and even with everything changing it is a third cheaper, mostly because ordering what it paints no longer costs what it did.

Where the gain comes from

A frame walks the element tree three times: build constructs it and asks for layout, prepaint resolves positions (layout happens here), paint emits the primitives handed to the GPU. These three are timed inside the frame with Instant, identically in every build measured here, so the compositor cannot distort them.

Prepaint falls from 2.83 ms to 0.43 ms at rest, and paint loses 40–50% at every share of change — 3.34 ms to 1.98 ms at rest, 3.35 ms to 1.71 ms with every cell changing. In a still frame, layout costs close to nothing: retained nodes are left alone. Paint did not move for a long time, because what it spent was ordering: every primitive is placed in a tree that finds what it overlaps, and that tree had grown thirteen levels deep where five would do. Kept balanced, it costs far less, whether or not anything changed. The phases add up to a little less than the main-thread time above; the rest is presenting the frame.

Scrolling a wide table

Four lists side by side, each row 24 text cells wide, 109 rows in view and 6000 layout nodes, scrolled by a fixed amount every frame. Rows are keyed by index or not keyed at all, because what applications write is mostly the second. Every row has text of its own, so a row scrolling back into view cannot borrow a neighbour's shaping.

Retaining layout made unkeyed scrolling three times slower before it made it faster. "Before these steps" is the tree this report was first written about. A scrolled list of rows without an id cost 23.76 ms a frame there, against 8.22 ms as extracted, and 5% of frames took over 46 ms — a slowly dragged list stuttered every time it crossed a row. Retained text nodes had stopped asking the line cache for their lines, so the cache forgot them, and every row that moved into a neighbour's node shaped its text again. The steps below that fix it are the reason this table exists.

Two steps carry most of the grid: keeping layout nodes (−32% at rest) and keeping the bounds tree balanced (−17% at rest, −23% with everything changing). Two carry most of the scrolling: handing a retained node's lines back to the cache (−64% unkeyed) and matching unidentified list items by their index (−38% more). The measurement closure, the style fingerprint and releasing what removed nodes held each take another 4–14% off whichever workload they touch, and taking a line wrapper only for text that truncates another 7% off a grid whose every cell changes.

A figure with a dotted underline comes from runs that disagreed by more than 6%: the machine switched speed while that build was being measured, and its median, and the changes on either side of it, can be off by that much. Hover it for the range of its five runs.

Not everything went one way. Keeping layout nodes costs 3% when every cell changes: a retained node pays for being found again — its key hashed, its style and children compared, its text keyed — and when nothing can be reused, that is all it gets. The build phase shows more than that, 0.29 ms, but most of it only moved there: extracted gpui dropped every measurement closure and text layout when it cleared the whole tree at the end of a frame, where no phase timer sees it, and a retained node drops its old ones as it is given new ones. A 10% loss for recolouring without reshaping, seen at 25% changing in the first round of measurements, did not survive seven more rounds of each build, which both put at 6.63 ms: that was a slow stretch of the machine, not the change. "Handing lines back" was later replaced by keeping lines cached while something holds them, which does the same job at a fraction of the cost.

Produced by cargo run -p gpui --example grid_frames --release -- 50 50 <percent> and cargo run -p gpui --example scroll_frames --release -- uniform <motion> <speed> <keying> 10000 0 20 4. Every build was compiled from its own commit with the same two examples and the same phase timer added to Window::draw_roots, then run alternately, rotating the order each round; each figure is the median of five runs. The median rather than the best: this machine runs the same binary in one of two speeds from one stretch to the next, and the best of a few runs reports whichever stretch a build happened to land in. The processor clocks down with a light load, so builds were only compared on workloads heavy enough to keep it at speed.
