A 120 Hz display gives a frame 8.33 ms, and the wall clock never reports less than that, so builds are compared on the CPU time the main thread spends on each frame — where gpui builds, lays out and paints. Extracted gpui used nearly all of it: the grid ran at the edge of the refresh whether it was still or changing. Now the still grid takes less than half the frame, and one where every cell changes two thirds of it.

The gain tracks how much actually changed

The horizontal axis is the share of cells whose text differs from one frame to the next. The baseline is a flat line: it costs the same whether anything changed or not, because it rebuilt every layout node and reordered every primitive either way. The current tree follows the real workload — the quieter the interface, the cheaper the frame — and even with everything changing it is a third cheaper, mostly because ordering what it paints no longer costs what it did.

Where the gain comes from

A frame walks the element tree three times: build constructs it and asks for layout, prepaint resolves positions (layout happens here), paint emits the primitives handed to the GPU. These three are timed inside the frame with Instant, identically in every build measured here, so the compositor cannot distort them.

Prepaint falls from 2.88 ms to 0.55 ms at rest, and paint from 3.34 ms to 0.98 ms at rest and from 3.35 ms to 1.73 ms with every cell changing. In a still frame, layout costs close to nothing: retained nodes are left alone. Paint did not move for a long time, because what it spent was ordering: every primitive is placed in a tree that finds what it overlaps, and that tree had grown thirteen levels deep where five would do. Kept balanced, it costs far less whether or not anything changed, and when nothing moved it is not consulted at all: the orderings a frame asks for are the ones the last frame was given. The phases add up to a little less than the main-thread time above; the rest is presenting the frame.

Build at rest is higher now than as extracted, 1.69 ms against 1.40 ms, though nothing in it got slower: the frame got light enough for the processor to clock down, and the same work takes longer at a lower clock. With another core kept busy, which holds the clock up, build takes 1.03 ms and the whole still frame 2.30 ms, against 5.05 ms for the tree before the bounds tree was kept balanced, under the same conditions. Every figure here is at whatever clock the processor chose, so the lightest frames understate what was saved.

Retaining layout made unkeyed scrolling three times slower before it made it faster. "Before these steps" is the tree this report was first written about. A scrolled list of rows without an id cost 23.57 ms a frame there, against 7.82 ms as extracted, and 5% of frames took over 45 ms — a slowly dragged list stuttered every time it crossed a row. Retained text nodes had stopped asking the line cache for their lines, so the cache forgot them, and every row that moved into a neighbour's node shaped its text again. The steps below that fix it are the reason this table exists.

Scroll columns are the wide table going back and forth at 12 px/frame, unkeyed and keyed by index, and scrolling one way at 48 px/frame unkeyed.

Two steps carry most of the grid: keeping layout nodes (−32% at rest) and keeping the bounds tree balanced (−18% at rest, −23% with everything changing). Two carry most of the scrolling: handing a retained node's lines back to the cache (−66% unkeyed) and matching unidentified list items by their index (−35% more). The measurement closure, the style fingerprint and releasing what removed nodes held each take another 2–11% off whichever workload they touch, and taking a line wrapper only for text that truncates another 7% off a grid whose every cell changes. Keeping a native font per size takes 27% off scrolling at 48 px/frame and 5% off scrolling back and forth: those are the workloads that bring new text into view every frame, and shaping it no longer starts by rebuilding the caches CoreText keeps on a font.

Handing out last frame's orderings takes 10% off the grid at rest, and only there. It pays off for a frame whose every primitive lands exactly where it did the frame before — one where only colours, opacities or hover states changed. A frame where anything moves or changes size, even one label growing by a digit's width, stops matching at that primitive and orders the rest as before, having paid up to 1% to find out.

A figure with a dotted underline comes from runs that disagreed by more than 6%: the machine switched speed while that build was being measured, and its median, and the changes on either side of it, can be off by that much. Hover it for the range of its five runs.

Not everything went one way. Keeping layout nodes costs 1–3% when every cell changes: a retained node pays for being found again — its key hashed, its style and children compared, its text keyed — and when nothing can be reused, that is all it gets. The build phase shows more than that, 0.31 ms, but most of it only moved there: extracted gpui dropped every measurement closure and text layout when it cleared the whole tree at the end of a frame, where no phase timer sees it, and a retained node drops its old ones as it is given new ones. A 10% loss for recolouring without reshaping, seen at 25% changing in the first round of measurements, did not survive seven more rounds of each build, which both put at 6.63 ms: that was a slow stretch of the machine, not the change. "Handing lines back" was later replaced by keeping lines cached while something holds them, which does the same job at a fraction of the cost.

In an application: gpui-kit's data table

The benchmarks above are labels and rows without an id. gpui-kit's DataTable story is what an application looks like instead: a 5000-row table of quotes whose cells carry ids, hover states and click handlers, with 30% of its first 2000 rows given new values 30 times a second. Most of its elements are identified, and every one of them looks its state up by its path of ids several times a frame, which is work none of the steps above touch.

Figures are milliseconds of main-thread CPU per second spent in Window::draw, recorded with samply at 4 kHz: two runs of 20 s for each build, all in one session, the same gpui-kit code built against each. Under each figure are the change against the row above and, marked total, against gpui-pre, the crates.io snapshot gpui-kit used before it moved to this tree. The window draws about 24 frames a second in a debug build and 29 in a release build, set by the refresh timer.

Two of these steps are upstream gpui's, from the snapshot gpui-pre was cut from and newer than the one this tree was extracted from. Building an inspector id copied the whole element id stack and hashed it into a map, and looking up inspector state cloned every div's base style, for every element in every frame, with the inspector closed. Both are compiled in only for debug builds or with the inspector feature, so neither reached the benchmarks above; but cargo run is a debug build, and gpui-kit's workspace turns the feature on for its release builds too. They are why this tree drew the table 12% slower than gpui-pre in a debug build before these steps.

Hashing an id's path once takes 14% off the debug build and 9% off the release one. Element state is looked up by an element's global id in request layout, prepaint and paint, each lookup hashing it to take the state out of last frame's map, again to put it in this frame's, and once more when the frame is finished — twelve times a frame for a path of names hashed byte by byte. The path's hash is now worked out when the id is made, and the id hashes to it. GlobalElementId loses DerefMut, which would let its path change under its hash; nothing in this tree or in gpui-kit used it.

The inspector-state step measures +3% in the debug build, within what two runs of the same build differ by there; in the release build it takes 6%. A debug build spends about as much of its main thread generating the story's random quotes as drawing them, in crates the debug profile does not optimise, so its CPU use as a whole moves about half as much as its drawing does. samply's sampling also keeps the processor clocked up, so these figures are lower than what a system monitor shows for the same window, where a lightly loaded processor clocks down and the same work takes longer.

Produced by cargo run -p gpui --example grid_frames --release -- 50 50 <percent> and cargo run -p gpui --example scroll_frames --release -- uniform <motion> <speed> <keying> 10000 0 20 4. Every build was compiled from its own commit with the same two examples and the same phase timer added to Window::draw_roots, then run alternately, rotating the order each round; each figure is the median of five runs. The median rather than the best: this machine runs the same binary in one of two speeds from one stretch to the next, and the best of a few runs reports whichever stretch a build happened to land in. The processor clocks down with a light load, so builds were only compared on workloads heavy enough to keep it at speed.
