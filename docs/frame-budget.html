A 120 Hz display gives a frame 8.33 ms, and the wall clock never reports less than that, so builds are compared on the CPU time the main thread spends on each frame — where gpui builds, lays out and paints. Extracted gpui used all of it: the still grid ran at the edge of the refresh, and with every cell changing it dropped frames. Now the same grid leaves more than half the frame free.

The gain tracks how much actually changed

The horizontal axis is the share of cells whose text differs from one frame to the next. The baseline is a flat line: it costs the same whether anything changed or not, because it rebuilt every layout node and reordered every primitive either way. The current tree follows the real workload — the quieter the interface, the cheaper the frame — and even with everything changing it is a quarter cheaper, because ordering what it paints no longer costs what it did.

Where the gain comes from

A frame walks the element tree three times: build constructs it and asks for layout, prepaint resolves positions (layout happens here), paint emits the primitives handed to the GPU. These three are timed inside the frame with Instant, identically in every build measured here, so the compositor cannot distort them.

Prepaint falls from 2.94 ms to 0.56 ms at rest, and paint halves at every share of change — 3.33 ms to 1.67 ms. In a still frame, layout costs close to nothing: retained nodes are left alone. Paint did not move for a long time, because what it spent was ordering: every primitive is placed in a tree that finds what it overlaps, and that tree had grown thirteen levels deep where five would do. Kept balanced, it costs half as much, whether or not anything changed. The phases add up to a little less than the main-thread time above; the rest is presenting the frame.

Scrolling a wide table

Four lists side by side, each row 24 text cells wide, 109 rows in view and 6000 layout nodes, scrolled by a fixed amount every frame. Rows are keyed by index or not keyed at all, because what applications write is mostly the second. Every row has text of its own, so a row scrolling back into view cannot borrow a neighbour's shaping.

Retaining layout made unkeyed scrolling three times slower before it made it faster. "Before these steps" is the tree this report was first written about. A scrolled list of rows without an id cost 23.56 ms a frame there, against 8.19 ms as extracted, and 5% of frames took over 45 ms — a slowly dragged list stuttered every time it crossed a row. Retained text nodes had stopped asking the line cache for their lines, so the cache forgot them, and every row that moved into a neighbour's node shaped its text again. The steps below that fix it are the reason this table exists.

Scroll columns are the wide table going back and forth at 12 px/frame, unkeyed and keyed by index, and scrolling one way at 48 px/frame unkeyed.

Two steps carry most of the grid: keeping layout nodes (−33% at rest) and keeping the bounds tree balanced (−25% at rest, −21% with everything changing). Two carry most of the scrolling: handing a retained node's lines back to the cache (−66% unkeyed) and matching unidentified list items by their index (−35% more). The measurement closure, the style fingerprint and releasing what removed nodes held each take another 3–10% off whichever workload they touch.

Not everything went one way. Recolouring without reshaping costs the grid 10% when a quarter of it changes, and keeping layout nodes cost 3% when all of it changes; both are still in the tree, outweighed by the steps after them. "Handing lines back" was later replaced by keeping lines cached while something holds them, which does the same job at a fraction of the cost.

Produced by cargo run -p gpui --example grid_frames --release -- 50 50 <percent> and cargo run -p gpui --example scroll_frames --release -- uniform <motion> <speed> <keying> 10000 0 20 4. Every build was compiled from its own commit with the same two examples and the same phase timer added to Window::draw_roots, then run alternately, rotating the order each round; each figure is the best of three, because interference only ever makes a frame slower. The processor clocks down with a light load, so builds were only compared on workloads heavy enough to keep it at speed.
